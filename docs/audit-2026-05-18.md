**Date**: 2026-05-18

**Scope**: Production-readiness with emphasis on payment processing

## Anti-Patterns Verdict

The backend is **not** AI-slop — it is evidently hand-crafted with carefully
thought-through invariants (append-only triggers, separate-connection
refund-attempt logs, `FOR UPDATE` locks, idempotency keys, partial unique
indexes). What it has instead is the inverse problem: a few specific,
named, *documented* hazards that haven't been fully closed. The README
"Reconciling failed Autumn refunds" section (lines 193–244) is essentially
the code admitting the window exists and pushing recovery onto an operator.

The **CORS configuration** in `netlify.toml` is the one section that smells
AI-templated — wildcard origin AND credentials is a contradictory pair the
spec forbids.

## Executive Summary

**Top issues**:

1. `findGiftRecipient` queries the dropped column `users.email` →
   `/api/stamps/gifts/checkout` 500s for any non-email recipient (P0).
2. Autumn webhook can double-credit on concurrent retries:
   `hasStampCheckout()` is not atomic with the credit (P1).
3. Resend bounce webhook can double-refund on retry:
   `refundFailedSend` + `markFailedRefunded` are sequential, not
   transactional, and `refundFailedSend` is not idempotent (P1).
4. CORS is `Access-Control-Allow-Origin: *` AND
   `Access-Control-Allow-Credentials: true` (P1).
5. No CSP / HSTS / X-Frame-Options / rate limiting on any endpoint (P1).
6. 10-minute "resurrection" window in `postcards/send.ts` can double-debit
   if a genuinely slow send completes after the user retries (P1).

The single-user purchase + share + postcard path is well-instrumented.
Gift checkout is broken. CORS + missing headers + no rate limiting
widen the blast radius of anything that does go wrong.

## Detailed Findings

### P0 — Blocking

#### P0-1. Gift checkout selects from dropped column `users.email`

- **Location**: `netlify/lib/billing.ts:160-185` (`findGiftRecipient`),
  called from `netlify/functions/stamps/gifts/checkout.ts:36`.
- **Category**: Data integrity / payments correctness.
- **Impact**: Every call to `POST /api/stamps/gifts/checkout` with a
  Bluesky handle (not an email) raises `column "email" does not exist`
  and returns 500. The pending-gift path (email recipient) goes through
  and creates Autumn checkouts that **cannot ever resolve to a known user
  account**: recipients who already have a drerings account will never
  get the stamps credited. `CLAUDE.md` flags this; `test/us017-*` files
  use `describe.skip` against it.
- **Recommendation**: Replace the email lookup with a handle/DID resolver:
  accept Bluesky handle or DID input, normalize, resolve against
  `users.handle` or `users.did`. Update `createGiftCheckoutSession`
  metadata — `gift_recipient_email` is no longer derivable; either drop
  it or synthesize from handle (matches `billing.ts:110` pattern for the
  buyer). Un-skip the three `us017` tests after.
- **Workaround until fixed**: Return 404 from
  `/api/stamps/gifts/checkout` for non-email recipients rather than 500,
  so the UI shows a clean error.

### P1 — Major

#### P1-1. Autumn webhook credit is not atomic — concurrent retries can double-credit

- **Location**: `netlify/lib/billing.ts:423-487` (`applyStampCheckout`).
  `hasStampCheckout()` and `creditStampLot()` run on separate connections
  with no lock between them.
- **Category**: Payments correctness.
- **Impact**: Svix delivery retries are common (Autumn will resend on any
  5xx or timeout). Two concurrent deliveries of the same
  `checkout.completed` event:
  1. Both call `hasStampCheckout(checkoutId)` → both return `false`.
  2. Both call `creditStampLot(...)` → both insert lots and increment
     `users.stamps_balance` by `pack.count`.
  3. Result: buyer gets 2× the stamps for one payment.
  `verify-stamp-invariants` would flag the drift the next day, not in
  time.
- **Recommendation**: Add a UNIQUE constraint on the natural key. Options:
  - `UNIQUE (stamp_lots.autumn_checkout_id)` partial-indexed where
    `source IN ('purchase','gift_received')`; OR
  - `UNIQUE (stamp_transactions.reference_id, reason)` for
    `reason IN ('purchase','gift_sent','gift_received')`.
  Then wrap the `hasStampCheckout` check inside `creditStampLot`'s
  transaction OR rely on UNIQUE+`ON CONFLICT` and treat conflict as
  `'already_credited'`.

#### P1-2. Resend bounce webhook is non-idempotent — can double-refund

- **Location**: `netlify/lib/resend-webhook.ts:92-101`. Sequence is
  `refundFailedSend(...)` → `markFailedRefunded(...)`, **not** wrapped in
  a transaction.
- **Category**: Payments correctness.
- **Impact**: If `markFailedRefunded` fails (or the function times out
  between the two calls), Resend retries the webhook. The retry passes
  the `status === 'failed_refunded'` guard because the row is still
  `'sent'`, so `refundFailedSend` runs again — incrementing the lot and
  `users.stamps_balance` by 1 per retry. `refundFailedSend`
  (`stamps.ts:810-866`) has no dedupe key.
- **Recommendation**: Either (a) wrap both operations in a single
  transaction (pass a shared `client` to `refundFailedSend` mirroring
  the `debitStamp(client?)` pattern), or (b) add a UNIQUE constraint
  on `stamp_transactions (lot_id, reason)` for
  `reason = 'failed_send_refund'`, treating conflict as already-applied.

#### P1-3. CORS is wildcard origin + credentials

- **Location**: `netlify.toml:1-8`.
- **Category**: Security.
- **Impact**: Per the CORS spec, modern browsers should reject this
  combination, so cookies don't actually get sent cross-origin today.
  But (a) this signals intent confusion and any future header tweak
  could open the hole, (b) non-credentialed cross-origin reads work,
  exposing API surface to any origin, (c) non-browser clients won't
  honor the browser-side block.
- **Recommendation**: Set `Access-Control-Allow-Origin` to the exact
  `PUBLIC_URL` (production) / `http://localhost:8888` (local) and drop
  `Authorization` from `Allow-Headers` if unused. Remove
  `Access-Control-Allow-Credentials: true` unless cross-origin
  authenticated requests are an actual product requirement (the SPA is
  same-origin via `/api/*` redirects, so likely not).

#### P1-4. Missing security headers (CSP / HSTS / X-Frame-Options / Referrer-Policy)

- **Location**: `netlify.toml`.
- **Category**: Security.
- **Impact**: Cookies are `HttpOnly`, so XSS can't steal them. But XSS
  *can* still issue authenticated `fetch('/api/postcards/send', …)`
  calls and burn the victim's stamps. Without
  `frame-ancestors`/`X-Frame-Options`, clickjacking can trigger
  one-click actions (e.g., the Buy Pack modal). Without HSTS, a
  network-positioned attacker can downgrade.
- **Recommendation**: Add to `netlify.toml`:
  - `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`
  - `Content-Security-Policy: default-src 'self'; script-src 'self';`
    ` style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;`
    ` connect-src 'self'; frame-ancestors 'none'; base-uri 'self'`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `X-Content-Type-Options: nosniff`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=()`

#### P1-5. No rate limiting on any endpoint

- **Location**: All `netlify/functions/`.
- **Category**: Security / cost control.
- **Impact**:
  - `/api/auth/login?handle=` — handle-enumeration / PDS-flood vector.
  - `/api/postcards/send` — a compromised account with N stamps can
    immediately drain them and Resend's quota.
  - `/api/billing/checkout` and `/api/stamps/gifts/checkout` — every
    call creates a real Autumn Checkout session (rate-limit pressure on
    Autumn's API + each call writes `autumn_customer_id`).
  - `/api/shares/confirm` — debits stamps.
- **Recommendation**: Per-user / per-IP rate limits at the edge (Netlify
  Edge Functions, or a shared in-process limiter in DB if simpler).
  Suggested envelopes: 10/min on `login` per IP, 30/min on
  `postcards/send` per user, 5/min on `checkout` per user.

#### P1-6. Postcard "10-minute resurrection" enables double-debit

- **Location**: `netlify/functions/postcards/send.ts:98-111`.
- **Category**: Payments correctness.
- **Impact**: When a queued postcard older than 10 min is found, the
  code "proceeds with a fresh attempt" on the **same** `postcard.id`,
  calling `debitStamp({ userId, referenceId: postcard.id })` again. The
  original attempt is not cancelled — it could still be running (Resend
  tail latency, retried HTTP). If both complete, `debitStamp` runs twice
  → 2 stamps consumed, but `attachLotAndMarkSent` only stores one
  `lot_id`. User sees one postcard, paid two stamps. The invariant
  check would NOT catch this — `stamp_lots` and `stamp_transactions`
  agree the user spent 2; it's the *business* invariant ("one debit per
  postcard.id") that's violated.
- **Recommendation**: Either (a) require the resurrection path to
  delete-and-recreate the postcard row so a fresh `id` is used, (b)
  gate `debitStamp` with a CAS on `postcards`
  ("set queued→debiting WHERE id=? AND status='queued'") so only one
  debiter wins, or (c) make `debitStamp` idempotent on
  `(referenceId, reason)`.

### P2 — Minor

#### P2-1. Refund-then-commit ordering in three sites

- **Location**:
  - `netlify/lib/stamps.ts:946-951` (`refundPurchasedStampLot`)
  - `netlify/lib/stamps.ts:1049-1054` (`refundSentGiftStampLot`)
  - `netlify/lib/stamps.ts:1137-1156` (`refundExpiredPendingGift`)
- **Category**: Payments correctness.
- **Impact**: `options.issueRefund(...)` runs **inside** the local
  transaction, before COMMIT. If Autumn refunds but the local COMMIT
  fails (network blip, pool exhaustion), the customer is refunded yet
  the stamp lot still shows `remaining_count > 0`. The
  `autumn_refund_attempts` row survives (separate connection, per the
  `billing.ts:248-249` comment), so a retry detects `status='succeeded'`
  and exits without re-refunding. Local state stays inconsistent until
  the daily `verify-stamp-invariants` job flags it.
- **Status**: Documented in README "Reconciling failed Autumn refunds"
  with manual SQL steps — **known and operationally mitigated**, hence
  P2, not P1.
- **Recommendation**: Reorder to:
  1. INSERT into `autumn_refund_attempts`,
  2. COMMIT local debit/lot/balance,
  3. Call Autumn,
  4. Mark attempt succeeded/failed.
  The natural-key dedupe in `autumn_refund_attempts` still prevents
  double-Autumn-refund, and the local ledger commits before the
  external side-effect.

#### P2-2. `.env` uses `AUTUMN_API_KEY`, code reads `AUTUMN_SECRET_KEY`

- **Location**: `.env` (line 2) vs `netlify/lib/billing.ts:623`.
- **Category**: Operability.
- **Impact**: Local dev silently falls back to mock checkout because
  `process.env.AUTUMN_SECRET_KEY` is undefined and
  `shouldUseMockCheckout()` returns `true` (NETLIFY_LOCAL is set).
  A developer wanting to exercise the real Autumn integration locally
  hits mock-mode without warning.
- **Recommendation**: Rename `.env` entry to `AUTUMN_SECRET_KEY`. Add a
  single startup log line describing which mode each integration is
  running in.

#### P2-3. `creditStampLot` throws opaque error on unknown `userId`

- **Location**: `netlify/lib/stamps.ts:537-543`. `UPDATE users …
  RETURNING stamps_balance` returns 0 rows; then
  `balanceResult.rows[0].stamps_balance` throws
  `Cannot read properties of undefined`.
- **Category**: Operability.
- **Impact**: Webhook for a user who's been deleted (or a stale
  `customer_id`) produces a confusing 500. Caught in the webhook
  handler and logged, but the error message is uninformative and the
  webhook gets retried indefinitely.
- **Recommendation**: Check `balanceResult.rowCount === 0`, throw a
  named `UserNotFoundError`. In `applyStampCheckout`, return
  `handled: true` with `stamp_purchase: 'orphaned'` so Autumn stops
  retrying.

#### P2-4. Drawing-ownership check is outside the share transaction

- **Location**: `netlify/functions/shares/confirm.ts:49`, then
  `recordShare` at `netlify/lib/shares.ts:153`. Ownership is checked
  via `postStore.userOwnsDrawing` on `db.pool` *before* the
  connection-bound transaction starts.
- **Category**: Payments correctness.
- **Impact**: TOCTOU. If a drawing is deleted between the ownership
  check and the share-insert, the FK with `ON DELETE CASCADE` on
  `share_events.drawing_id` mitigates the drift, but a malicious or
  buggy client could theoretically race. Practical exploitability is
  low.
- **Recommendation**: Move the ownership check inside the same
  transaction, after the `SELECT … FOR UPDATE` on users.

#### P2-5. No max-body-size or content-type guard

- **Location**: `netlify/lib/http.ts:27-37` (`parseJsonBody`).
- **Category**: Robustness.
- **Impact**: `JSON.parse` runs on `event.body` unconditionally.
  Netlify caps at 6 MB but the function still spends CPU on parse.
  Minor cost vector.
- **Recommendation**: Reject `Content-Type != application/json`. Cap
  body length earlier.

#### P2-6. `Cache-Control` headers not set on API responses

- **Location**: `netlify/lib/http.ts:3-14`.
- **Category**: Security / correctness.
- **Impact**: `/api/whoami` and `/api/stamps/...` responses contain
  personal balance + handle. Some intermediaries may cache.
- **Recommendation**: Add `Cache-Control: private, no-store` to the
  default `json()` helper.

### P3 — Polish

#### P3-1. `NETLIFY_LOCAL=true` in production accidentally enables mock checkout

- **Location**: `netlify/lib/billing.ts:519-524`.
- **Impact**: If `NETLIFY_LOCAL` ever leaks into a prod environment
  with `AUTUMN_SECRET_KEY` unset, real purchases would silently
  mock-credit stamps without any Autumn transaction.
- **Recommendation**: Defense-in-depth — require
  `NETLIFY_LOCAL && NODE_ENV !== 'production'`.

#### P3-2. `getPendingGiftSignupUrl` hard-codes `https://drerings.app` fallback

- **Location**: `netlify/lib/billing.ts:599-608`.
- **Impact**: If both `URL` and `DEPLOY_PRIME_URL` are unset (unusual
  on Netlify), gift signup emails point to the hard-coded prod domain
  from staging/local.

#### P3-3. Session cookie `issued_at` never validated server-side

- **Location**: `netlify/lib/session.ts:79-113`.
- **Impact**: HMAC validates payload integrity, but `getSession`
  doesn't check that `issued_at` is within the 14-day window. The
  browser honors `Max-Age`, but a leaked cookie value can be replayed
  indefinitely — there is no server-side TTL.
- **Recommendation**: In `readSignedSessionUser`, reject when
  `Date.now() - Date.parse(body.issued_at) > 14 days`.

#### P3-4. Two `console.log` calls in scheduled functions

- **Location**:
  - `netlify/functions/refund-expired-gifts.ts:13`
  - `netlify/functions/verify-stamp-invariants.ts:8`
- **Impact**: Summary counts (no PII). Inconsistent with the rest of
  the codebase using `console.error`/`console.warn`.

## Patterns & Systemic Issues

1. **External side-effects inside local transactions.** Three refund
   sites and the postcard-send path call external services (Autumn,
   Resend) while holding a Postgres client. The `autumn_refund_attempts`
   table + operator runbook are clever mitigations, but the underlying
   pattern recurs. **The general rule should be: write your intent
   locally, COMMIT, then perform the external call, then mark the
   intent done.**

2. **Idempotency keys exist on the request side but not always on the
   effect side.** `postcards` uses client-supplied idempotency keys;
   `share_events` does too. But `stamp_transactions.reference_id` is
   not unique, so the same `reference_id` can produce multiple ledger
   rows on retry — which is precisely the double-credit (P1-1) and
   double-refund (P1-2) failure mode.

3. **Tests for the broken thing are skipped, not removed.**
   `test/us017-*` `describe.skip` (3 files) point at a real product
   feature (`/api/stamps/gifts/checkout`) that is wired up in
   production. Either remove the route from the public surface until
   the bug is fixed, or fix and un-skip.

## Positive Findings

- **Append-only triggers on `stamp_transactions` and `share_events`**
  are a strong invariant — DB-level enforcement is the right place for
  "no mutations ever."
- **`autumn_refund_attempts` written via a separate connection** so it
  survives caller ROLLBACK is exactly the right pattern for
  external-side-effect bookkeeping. The decision table at
  `billing.ts:271-308` (succeeded / in-flight / orphaned / ambiguous)
  is thoughtfully complete.
- **`debitStamp(client?: DatabaseClient)`** — letting callers pass in
  a shared transaction is a clean way to compose share-event-insert +
  stamp-debit atomically.
- **Svix signature verification uses `timingSafeEqual`** on the decoded
  buffers (`svix.ts:74-94`) — no timing leak.
- **HMAC session signing** with `timingSafeEqual` on the comparison.
- **The README runbook for refund reconciliation** is genuinely useful
  operator documentation, not just security theater.
- **50+ user-story-tagged tests** with a tight `us0XX-feature.test.ts`
  naming convention.
- **Migration 0012 extended the `reason` CHECK constraint** when adding
  `'share'` — schema and code stayed in lockstep.
